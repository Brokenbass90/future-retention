# RetKit — студия писем

Студия для email-команды: собрать письмо из блоков, разложить по локалям,
отдать готовый HTML. Не конструктор для конечного пользователя — рабочий
инструмент, где рядом работают человек и его агент.

Node без фреймворков: `server.js` — один HTTP-сервер на 107 ручек, `src/*` —
модули с логикой, `public/*` — две поверхности без сборки (ES5-совместимый
браузерный JS, никаких бандлеров).

**Запуск:** `npm start` (порт 3000). **Проверка:** `npm test` — примерно 50
скриптов, каждый печатает `N ok, M fail` и возвращает код возврата.

## Карта

| Где | Что |
|---|---|
| `server.js` | HTTP-слой: маршруты, валидация запроса, ответы. Логике здесь не место |
| `src/` | Вся логика: сборка письма, каталог блоков, локали, замки, черновики, актёры |
| `public/constructor.*` | Конструктор: drag-n-drop сборка письма из блоков |
| `public/workbench.*` | Воркбенч: код письма, локали, предпросмотр, сборка |
| `data/block-library/` | Библиотека блоков: `canonical/` (ручные), `imported/` (из писем), `user/` |
| `data/block-previews/` | Пререндеренные PNG карточек каталога + `index.json` |
| `email-base/<BRAND>/mail-*/` | База писем: `app/templates/blocks/header.pug` + `app/styles/blocks/main.styl` |
| `email-base/vendor/` | Общий скелет писем и **локали**: `vendor/data/<locale>/<NS>.json` |
| `email-base/dist/` | Результат сборки. В репозитории ему не место |
| `email-base/tools/build-mail.js` | Сборщик: Pug + Stylus + локаль → HTML |
| `mcp/` | MCP-сервер студии: чужой Клод подключается и работает инструментами |
| `docs/WORK-ROADMAP.md` | Живой роадмап: что сделано, что следующее, чем проверяется |

## Железные правила

**1. К письмам — только через дверь.** Любое создание, запись, копирование,
переименование и удаление письма идёт через `src/mail-store.js`. Он знает пути,
спрашивает разрешение (замки, режим только для чтения) и не даёт выйти за
пределы базы. `scripts/test-mail-store-single-door.mjs` — храповик: число мест,
где путь в базу собирают вручную, зафиксировано по файлам и может только
уменьшаться. Новый код начинает с нуля.

**2. Правки существующего письма идут в черновик.** `src/mail-drafts.js`:
личная копия `mail-x__draft-<owner>` рядом с письмом, общая база меняется один
раз — публикацией, с показом разницы и снимком прежней версии в
`.retkit/history/`. Отсюда же берётся откат. Для агента это главное правило:
пиши в свой черновик, публикуй только когда человек попросил.

**3. Актёр и замки не обходятся.** Кто пишет — знает `src/actor.js` (метка в
cookie у человека, в заголовке `x-retkit-token` у агента). Занятость письма
держит `src/mail-locks.js`. Запись в чужое занятое письмо обязана падать с
`MAIL_LOCKED`, а не «побеждать». У одного человека локально два актёра: он сам
и его Клод — различать их обязательно.

**4. Формат блока — договор.** `{pug, styl, slots[], placement, category, kits,
slotPresets, childSlots}`, схема в `src/block-library-schema.js`. Ломать его под
удобство одной задачи нельзя: на нём стоят каталог, конструктор, превью и MCP.

**5. `vendor/` — источник, а не копия.** Скелет письма (head, footer, button,
ink, variables, mixins) и все локали живут там. Класть их копии в письмо не
нужно; в базе такие копии уже есть и их предстоит вычистить (этап 7 роадмапа).

**6. Проверка — часть работы.** На каждое изменение поведения — тест, и в
шапке теста написано, ЧЕГО он не даёт случиться, а не «проверяет функцию X».
Тест без объяснения опасности бесполезен: его удалят при первом неудобстве.

**7. Комментарии по-русски и про «почему».** В проекте так везде. Комментарий,
пересказывающий код, — мусор; комментарий, объясняющий причину решения и цену
альтернативы, — то, ради чего их пишут.

**8. Уборка в тестах не роняет тест.** На смонтированных файловых системах
`unlink` бывает запрещён. Не можете удалить — отодвиньте переименованием и
скажите об этом, но не валитесь на уборке, потеряв результат проверки.

## Как проверять

```bash
npm test                                  # весь прогон
node scripts/test-mail-locks.mjs          # один тест целиком
npm run test:blocks -- --only sys-        # блоки по фильтру
npm run audit:ui                          # элементы интерфейса без обработчиков
npm run previews -- --only sys-           # перерисовать превью блоков
```

Ворота, которые нельзя обходить: полный прогон зелёный, храповик путей не
растёт, превью есть у каждого блока каталога, а после чистки базы HTML всех
писем во всех локалях совпадает с эталоном побайтово.

Headless-браузера в окружении может не быть. Тогда вместо скриншота проверяйте
разметку через `linkedom`: файл интерфейса исполняется в DOM с подставным
`fetch` — видно ровно то, что увидел бы глаз. Пример — конец
`scripts/test-actor.mjs`.

## Если файлов студии не видно

Этот скилл читают две разные сущности, и им доступно разное.

**Claude Code, открытый в папке студии**, читает и правит файлы своими
средствами. Ему ничего из этого раздела не нужно — его инструменты лучше:
они видят весь репозиторий, знают про git и умеют писать.

**Клод, подключённый по MCP** (Claude Desktop и все прочие), файлов студии не
видит вовсе. Раньше это означало, что об устройстве студии он мог только
догадываться по названиям — и догадывался неверно. Теперь у него есть три
инструмента, и порядок такой:

1. `retkit_find_in_code` — найти место. Студия это сотни файлов, открывать их
   подряд бессмысленно. Пустой результат НЕ значит, что этого в студии нет:
   попробуйте часть слова или уберите сужение по пути.
2. `retkit_read_code` — прочитать вокруг найденного. Окном: `server.js` это
   двадцать тысяч строк, целиком его читать не нужно и не выйдет.
3. `retkit_list_code` — что вообще лежит в папке, если непонятно, куда идти.

Открыто только чтение и только код: `src`, `scripts`, `public`, `mcp`,
`tools`, `docs`, этот скилл. Письма, данные студии и всё похожее на ключи не
отдаются — письма читаются своими инструментами, знающими про замки и
черновики.

**Править код этими инструментами нельзя, и это не недоделка.** Правка по
сети идёт мимо git, мимо отката и мимо глаз человека — один неудачный заход
стоит дня работы. Нашли, что чинить, — опишите человеку место и правку, а
делает он её через Claude Code в папке студии.

## Глаза: не рассуждайте о внешнем виде вслепую

Каталог блоков описывает блок словами: id, назначение, имена слотов. Как он
выглядит, из этого не следует. Есть две картинки:

- `retkit_block_preview` — блок из каталога, десктоп и телефон.
- `retkit_render_mail` — снимок СОБРАННОГО письма из дерева блоков.

Прежде чем сказать человеку «выглядит хорошо» или обсуждать дизайн —
посмотрите. Мобильный вид снимайте отдельно (`view: mobile`): ломается он
чаще десктопного. Если у блока нет готового превью, это не повод описать его
вид по имени — соберите письмо и снимите.

## Руки: если нужного блока нет

Первый выбор — подобрать похожий и подогнать значения слотов. Новый блок
нужен, когда такой формы в каталоге нет вовсе.

Порядок: `retkit_block_source` у ближайшего соседа → `retkit_create_block`.
Смотреть соседа обязательно: вёрстка писем держится на таблицах и миксинах
семьи, блок «как на сайте» проверку не пройдёт. Исполняемый pug (`= value`,
`if`, циклы) запрещён — значения подставляются плейсхолдерами `{{ slot }}`.

Блок проходит ту же проверку, что и написанный руками. Не прошёл — остался
черновиком, в письмо не встанет; в ответе будет список претензий, их надо
починить и сохранить снова с `force: true`. Канонические блоки студии этой
ручкой не переписываются: правка канонического — это копия под новым id.

Создание и правка блока пишут на диск человека. Спрашивайте согласие до
вызова, а не после.

## Чего не делать

- Не писать в `email-base` мимо `src/mail-store.js`.
- Не удалять письма насовсем: они уходят в `email-base/_trash/`.
- Не публиковать чужой черновик и не публиковать свой без просьбы человека.
- Не коммитить `email-base/dist/` и `.retkit/` — это вывод и личные данные.
- Не трогать чужое занятое письмо «потому что мешает»: перехват — осознанное
  действие человека, а не умолчание агента.
- Не менять формат блоков и не переименовывать слоты без прогона `npm test`.
- Не заводить вторую реализацию того, что уже есть (второй чат, второй способ
  собрать путь, второй способ сохранить письмо) — в этом проекте так уже
  накопилось, и мы это разбираем, а не приумножаем.

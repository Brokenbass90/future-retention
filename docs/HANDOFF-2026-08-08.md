## Явные исключения из release commit

Не использовать `git add -A`. Не включать:

- `data/asset-registry.json` — resync добавил локальные `/studio-assets/...`,
  но соответствующие `data/assets/` gitignored и исчезнут на Heroku;
- `email-base/vendor/data/*/TESTEBTVOUMAT.json` — следы e2e-прогона;
- `tmp-brand.mjs`, `tmp-links.mjs`, `tmp-ui.mjs` и другие root tmp-файлы;
- `docs/HANDOFF-2026-07-27.md` — полезный черновик, но содержит устаревшую
  deploy-команду и неверную текущую дату;
- `docs/HANDOFF-CLAUDE-2026-07-20.md` и `docs/REVISION-2026-07-27.md` —
  исторические/дублирующие документы; их можно позже положить в архив;
- `docs/BLOCK-STYLE-DEPENDENCIES.md`, если отчёт не был заново сгенерирован
  после добавления полного IQ Broker-набора.

Также не включать случайные runtime SQLite/journal, локальные assets, `.env`,
backup и временные preview-mail каталоги.

## Рекомендуемая структура коммита

Один согласованный feature commit допустим, но scope должен быть виден до
коммита. Минимальные группы staging:

1. Код и тесты брендов/campaign/constructor/compose.
2. Canonical IQ/IQ Broker JSON и проверочная IQ Broker mail-base.
3. Generated preview index + все соответствующие PNG.
4. `docs/PROJECT-OVERVIEW.md` и этот handoff.

Перед коммитом:

```bash
git diff --cached --name-status
git diff --cached --check
git status --short
```

В unstaged должны остаться только заранее перечисленные пользовательские,
runtime и временные файлы. Если там появился неизвестный код — остановиться и
разобрать его, а не добавлять автоматически.

## Точная последовательность GitHub и Heroku

После зелёных проверок:

```bash
git commit -m "Expand branded email constructor and IQ Broker blocks"
git push -u origin codex/email-studio-release-gates
```

GitHub CLI для обычного push не нужен. Draft PR можно создать через GitHub UI,
GitHub connector или `gh`, если он установлен. Не вливать в `main` до просмотра
diff и результатов тестов.

Heroku принимает commit tree, а не незакоммиченные файлы. Разворачивать именно
проверенный HEAD текущей ветки:

```bash
git push heroku HEAD:main
heroku releases --app retention-tool-kit --num 5
curl -fsS https://retention-tool-kit-127e48dd48c6.herokuapp.com/healthz
```

Не использовать `git push heroku main`: локальный `main` может оставаться на
старом commit и развернуть не ту версию. Перед deploy сохранить номер текущего
Heroku release для rollback. После deploy проверить авторизованный UI,
конструктор, Workbench и один реальный build, а не только `/healthz`.

Если production smoke провален:

```bash
heroku releases --app retention-tool-kit --num 5
heroku rollback <PREVIOUS_RELEASE> --app retention-tool-kit
```

## P2 — известные риски после релиза

1. **Общий locale namespace при параллельной сборке.** Per-mail lock защищает
   одно письмо, но два разных письма с одинаковым namespace могут временно
   конкурировать за `email-base/vendor/data/<locale>/<namespace>.json`.
   Следующий шаг — namespace lock или полностью изолированный build workspace.
2. **Эфемерный Heroku filesystem.** Созданные в hosted UI письма, user blocks,
   SQLite и assets могут исчезнуть после restart/deploy. Нужны Postgres и
   S3/R2-совместимое хранилище.
3. **Preview churn и slug.** Каталог PNG меняет сотни бинарных файлов; текущий
   Heroku slug уже большой. Нужны детерминированная регенерация и вынос preview
   assets из slug либо отдельная политика хранения.
4. **RTL не закрыт реальными клиентами.** Трансформация и автотесты есть, но
   арабское письмо нужно проверять в Gmail, Outlook и Apple Mail, включая
   порядок колонок, кнопки, цифры, punctuation и mobile.
5. **Темы частично универсальны.** `$brand_*` приезжают в Stylus, но старые
   блоки всё ещё могут содержать жёсткие цвета.
6. **Detached HTML расходится с исходником намеренно.** Нужно сохранять явный
   статус, отдельную локаль, reset-to-Pug и release-аудит; не превращать
   detached в скрытую замену Pug.
7. **Image/Figma → email не production one-click.** AI должен сначала выдать
   proposal из существующих/кандидатных блоков и пройти visual diff; ручной
   Pug/Stylus контроль остаётся обязательным.
8. **Монолитный backend.** `server.js` стоит постепенно делить на API routes,
   orchestration и storage/build services после стабилизации релиза.

## Следующий продуктовый цикл

После выпуска этого scope лучше перейти к набору чистой базы:

1. Выбрать по одному реальному письму IQ Option и IQ Broker.
2. Нарезать атомы/секции/combo, дать им понятные слоты и брендовые токены.
3. Проверить desktop/mobile/RTL и реальные почтовые клиенты.
4. Только после этого approve и добавлять в основной каталог.
5. Параллельно развивать AI как proposal-инструмент: картинка/Figma → дерево
   блоков → visual diff → ручное принятие, а не прямой непроверенный HTML.

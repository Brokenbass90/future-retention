# Future Retention Studio — карта проекта

Актуально на 2026-08-08. Этот документ — каноническая карта продукта и его
технических границ. Операционный статус конкретного релиза хранится в текущем
`docs/HANDOFF-*.md`.

## Назначение

Future Retention Studio — рабочая среда для создания и сопровождения email-
писем на собственной базе `email-base`. Студия объединяет:

- визуальный трёхуровневый конструктор;
- библиотеку переиспользуемых блоков и готовых комбинаций;
- Pug/Jade + Stylus Workbench с локалями и итоговым HTML;
- темы брендов, изображения, ссылки и системные плейсхолдеры;
- AI-оператора, который работает через ограниченный набор проверяемых операций;
- сборку, аудит и выпуск email-safe HTML.

Принцип продукта: исходники и структурированная модель остаются доступными
человеку. AI помогает выбирать, создавать и править, но не становится скрытым
источником правды и не перезаписывает код без явного принятия изменений.

## Основной рабочий поток

1. Выбрать или создать бренд.
2. Открыть существующее письмо либо начать новое в конструкторе.
3. Собрать дерево из блоков или разложить готовое `комбо`.
4. Настроить тексты, изображения, ссылки, фон, рамки, радиусы и отступы.
5. Перейти в Workbench: первым рабочим исходником остаётся Pug/Jade, рядом
   доступны Stylus и локали.
6. Сохранить исходник и пересобрать связанный HTML.
7. При необходимости отвязать HTML конкретной локали и сделать финальную
   ручную правку. В интерфейсе такая версия явно помечается как detached и
   может быть сброшена обратно к Pug-сборке.
8. Перед копированием или скачиванием выполнить проверку всех локалей. Экспорт
   берёт байты из проверенного неизменяемого snapshot, а не из текущего preview.

## Конструктор: `outer → section → inner`

Структура письма — дерево, а не плоский список HTML-фрагментов.

| Уровень | Роль | Допустимое размещение |
|---|---|---|
| `outer` | каркас письма: head/preheader, ширина, общий фон, footer | корень канваса |
| `section` | самостоятельная строка/карточка/панель внутри письма | слот секций `outer` |
| `inner` | текст, заголовок, изображение, кнопка, список, колонки | именованный слот `section` |
| `combo` | рецепт из нескольких блоков и их связей | разворачивается в обычное дерево |

Комбо не должно оставаться непрозрачным монолитом: после вставки его дочерние
блоки редактируются и переставляются отдельно. Разделители тоже типизированы:
межсекционный разделитель занимает уровень `section`, внутренний разделитель —
слот внутри секции.

Правила размещения и сборки находятся главным образом в:

- `public/constructor.js` — канвас, дерево, drop-зоны и инспектор;
- `src/compose-email.js` — серверная сборка дерева;
- `src/constructor-build-policy.js` — политика фоновой и постоянной сборки;
- `data/block-library/canonical/*.json` — определения блоков и combo-рецепты.

Инспектор хранит почтовые цвета в явном `#RRGGBB`. `transparent` и наследование
разрешаются только там, где поле это поддерживает; `rgb()`, `rgba()` и
именованные цвета не должны попадать в Pug/Stylus как сохранённые значения.

## Workbench: исходники, сборка и ручной HTML

Workbench разделяет три состояния:

1. **Pug/Jade + Stylus** — основной редактируемый источник.
2. **Linked HTML** — результат текущей сборки исходников и локали.
3. **Detached HTML** — сохранённая ручная версия одной локали, сознательно
   отвязанная от Pug.

Переход в код не должен создавать обязательную «новую версию» письма. Сначала
открывается исходный `header.pug`/`header.jade`; изменение влияет на письмо
после безопасного сохранения и пересборки. Pug и Stylus сохраняются одной
транзакцией с проверкой исходной ревизии. Конфликт с более новой записью
заканчивается `409`, а не тихой потерей чужой работы.

Основные файлы:

- `public/workbench.js`, `public/workbench.html`, `public/workbench.css`;
- `src/code-workspace.js` — чтение и сохранение исходников/HTML;
- `src/workbench-source-transaction.js` — атомарная запись Pug и Stylus;
- `src/workbench-mail-operation-lock.js` — сериализация операций письма;
- `src/workbench-release-preflight.js` — проверка локалей перед выпуском.

## Контракт CSS и вес письма

Стили письма собираются из Stylus и email-framework слоя. После компиляции:

- обычные селекторы инлайнятся в элементы;
- в `<head>` остаются только правила, которые нельзя корректно инлайнить:
  `@media`, `@supports`, `@font-face`, `@keyframes`, а также явные
  client-specific/Outlook-правила;
- мобильный адаптив и необходимые хаки не выбрасываются;
- неиспользуемый обычный CSS не должен механически переноситься в `<head>`.

Текущие release-пороги:

- предупреждение по HTML начинается с 80 KiB;
- выпуск блокируется при размере 102 KiB и выше;
- большой head-CSS отдельно предупреждается от 20 KiB.

Реализация: `email-base/tools/build-mail.js`. Порог считается по фактическому
компактному UTF-8 HTML каждой локали. Это снижает риск Gmail clipping и не даёт
считать лёгким письмо только потому, что исходный Pug короткий.

## Бренды, темы и папки

`data/brands.json` — реестр брендов. Запись определяет id/папку, подпись,
активность, семейство блоков и HEX-токены темы:

- `primary`, `primary_text`;
- `text`, `muted`;
- `background`, `surface`;
- `border`, `link`.

Полоса брендов в конструкторе задаёт рабочий контекст:

- целевую папку при сохранении;
- видимость семейства блоков;
- фирменные цвета;
- папку по умолчанию в базе писем.

Новый бренд создаётся вместе с папкой `email-base/X_*`. Тема передаётся в
Stylus как `$brand_*`. Инфраструктура универсальных блоков готова, но не каждый
существующий блок уже переведён с жёстких цветов на токены — это отдельная
проверяемая миграция.

Frontend реестра: `public/brand-bar.js`. Серверная нормализация и хранение:
`src/brands.js`. База писем группируется по брендам, но физическим источником
правды остаются каталоги `email-base/X_*/mail-*`.

## Библиотека блоков и approval

| Источник | Путь | Политика |
|---|---|---|
| canonical | `data/block-library/canonical/` | доверенная выпускаемая библиотека |
| imported | `data/block-library/imported/` | legacy/quarantine, поиск и изучение, не release |
| user | `data/block-library/user/` | ручные/AI-блоки через `draft → candidate → approved` |

Новый ручной или AI-блок автоматически скоупит собственные классы, проходит
schema/security/Pug/Stylus/email-safe проверки и сохраняется как `candidate`.
В release-сборке разрешены canonical и только актуально approved user-блоки.
Изменение байтов блока меняет source hash и сбрасывает доверие к старому
approval. Imported-блок не может объявить себя canonical полем внутри JSON.

Ключевые модули:

- `src/block-library-schema.js`;
- `src/block-library-review.js`;
- `src/block-styles-from-mail.js` и style-registry слой;
- `src/compose-email.js`.

## Превью блоков

`scripts/render-block-previews.mjs` строит desktop (600 px) и mobile (375 px)
PNG. `data/block-previews/index.json` связывает изображение с хешем исходника,
слотами и визуальными признаками. Конструктор показывает крупный просмотр,
переключение desktop/mobile, слоты и исходный Pug/Stylus.

Preview-индекс и PNG — единый generated artifact: нельзя выпускать новый
индекс со старыми картинками или наоборот. Для canonical-релиза проверяется
свежесть превью. Массовую регенерацию нужно держать отдельным обозримым
изменением, потому что она меняет сотни бинарных файлов.

## IQ Option и IQ Broker

- `X_IQ` / семейство `iq` — основная текущая библиотека IQ Option.
- `X_IQBroker` / семейство `iqbroker`, префикс блоков `iqbr-` — отдельная тема
  и отдельный набор атомов/секций/combo.

IQ Broker `mail-strategies` нарезается воспроизводимыми скриптами из
`scripts/iqbroker-cut/`. Результат для ручной проверки лежит в
`email-base/X_IQBroker/mail-strategies-blocks/`. Брендовая фильтрация не должна
подставлять IQ Option-обёртку в письмо IQ Broker и наоборот.

## Ссылки и метка кампании

Конструктор собирает URL-слоты письма в одном диалоге. Поле campaign отдельно
нормализует собственную метку в `afftrack`/`retrack`, чтобы новое письмо не
унаследовало метки исходного блока. Платформенные плейсхолдеры не заменяются.

Контракт реализован в `src/campaign-links.js`, передаётся через
`src/compose-email.js` и сохраняется рядом с деревом в `studio-model.json`.

## AI-оператор: разрешённые действия

AI работает через `src/ai-agent.js` и явные инструменты `src/ai-tools.js`.
Он может:

- читать открытый HTML, namespace и locale-блоки;
- анализировать письмо, сравнивать и выравнивать локали;
- создавать/редактировать/переводить locale TXT и расставлять плейсхолдеры;
- искать точное место и предлагать хирургический replace/insert/remove HTML;
- искать блоки по метаданным и внешнему виду, читать их исходники;
- сохранить новый user-блок как candidate;
- обновить слоты конкретного блока канваса;
- собрать новое письмо из разрешённых блоков;
- завершить staged-набор изменений для показа пользователю.

Кодовые изменения показываются как proposal/diff с принятием или отказом.
Оператор не должен сам подтверждать overwrite, approve блока, release, Git push
или Heroku deploy. Сборка по изображению/Figma пока является управляемым
design-to-block процессом, а не гарантированным one-click production import.

## Источники правды

| Данные | Источник правды |
|---|---|
| письма и исходники | `email-base/X_*/mail-*/app/` |
| локали | `email-base/vendor/data/<locale>/<namespace>.json` |
| дерево конструктора | `email-base/X_*/mail-*/studio-model.json` |
| canonical/imported/user blocks | `data/block-library/<source>/` |
| брендовые темы | `data/brands.json` |
| preview metadata/PNG | `data/block-previews/index.json`, `data/block-previews/**` |
| runtime journal/SQLite | `data/studio.db*` — локально, не Git |
| загруженные локальные assets | `data/assets/` — локально и пока не durable |

`data/asset-registry.json` без соответствующих файлов `data/assets/` не является
переносимым production-состоянием. На Heroku файловая система эфемерна; до
подключения Postgres/object storage Git остаётся источником правды только для
явно закоммиченных писем, блоков и конфигурации.

## Release gates

Перед выпуском должны пройти:

1. `git diff --check` и проверка staged scope.
2. `npm test`.
3. `npm run test:constructor-tree`.
4. `npm run test:blocks`.
5. Проверка свежести canonical previews.
6. Workbench release-preflight всех локалей, включая detached HTML.
7. Ручной desktop/mobile/RTL smoke ключевого письма.
8. После deploy: номер Heroku release, `/healthz` и защищённый UI/API smoke.

Копирование и скачивание HTML работают только через проверенный snapshot
`locale → exact HTML bytes + SHA-256`. Изменение preview/cache после аудита не
должно менять экспортируемые байты.

## Известная следующая работа

- закончить визуальную проверку RTL/арабской типографики на реальных письмах;
- перевести выбранные блоки на брендовые `$brand_*` токены;
- сделать durable-хранилище: Postgres + S3/R2-совместимые assets;
- сократить бинарный churn и вес preview-каталога/Heroku slug;
- сериализовать сборки, которые используют один locale namespace из разных
  писем, либо сделать build workspace полностью изолированным;
- довести design/Figma/image-to-email до proposal с измеримой pixel-diff
  проверкой, но сохранить ручной Pug/Stylus контроль;
- наращивать новую чистую базу писем и canonical-блоков по одному бренду,
  не возвращая в release сломанный legacy-каталог;
- добавить обязательную матрицу реальных почтовых клиентов: Gmail web/mobile,
  Outlook Windows/web и Apple Mail;
- постепенно разделить большой `server.js` на маршруты и сервисы.

Дополнительные спецификации находятся в `docs/`, но при конфликте с этой
картой и текущим handoff сначала проверяется фактический код и тесты.

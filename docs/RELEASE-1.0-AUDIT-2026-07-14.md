# RetKit Studio — аудит готовности к 1.0

Дата: 2026-07-14

Этот документ фиксирует текущее состояние после аудита конструктора,
Workbench, локалей, библиотеки блоков, сборки и AI. Он дополняет старые
roadmap-документы: при расхождении фактическое поведение кода и этот аудит
считаются актуальнее ранних концептов.

## Короткий вывод

Идея продукта жизнеспособна: уже есть замкнутый путь
`блоки → Pug/Stylus → локали → HTML → ручная правка/экспорт`. Для внутренней
beta студия пригодна. Для маркировки `1.0` ещё нужны эксплуатационные гарантии:
версионирование изменений, постоянное хранилище, проверка в реальных почтовых
клиентах, строгие release-gates и прозрачная AI-телеметрия.

Главный продуктовый принцип для 1.0:

> Детерминированные операции выполняются без AI. AI только предлагает
> содержательные изменения; пользователь видит diff, подтверждает применение и
> может откатить результат.

## Что исправлено этим проходом

- Конструктор больше не запускает двойную сборку `--pretty` для iframe-preview.
- Preview-сборки получили очередь с приоритетами, лимит параллельности,
  объединение одинаковых запросов, короткий LRU-кэш и очистку временных папок.
- Повтор идентичного preview обслуживается из памяти; активный canvas имеет
  приоритет над миниатюрами каталога.
- Пустой canvas инвалидирует уже запущенный preview: поздний ответ больше не
  возвращает удалённый кусок письма в iframe.
- `⚡ После секции` переименован в понятное `Авто → Внутри` и снабжён точным
  описанием. Автопереключение происходит после добавления готовой секции, а не
  при обычном выборе существующего блока.
- Добавлены два разных разделителя: section-разделитель между секциями/комбо и
  inner-разделитель внутри секции. У обоих доступны высота и цвет промежутка.
- Наружная обёртка получила управляемый фон; значение по умолчанию `#F9F9F9`
  применяется к реальным `body`, `table.body` и внешней ячейке scaffold.
- Выравнивание canonical image/logo/date теперь записывается одновременно в
  email-атрибут и inline `text-align`, поэтому работает в preview и сборке.
- Исправлен RTL-проход: глобальный CSS в `<head>` не зеркалится, URL и порядок
  картинок не меняются, `<bdi>` не попадает в атрибуты, повторный RTL-проход
  идемпотентен.
- Campaign-specific плейсхолдеры удалены из reusable canonical-комбо и inner-
  блоков. Системные плейсхолдеры остаются в footer, где они действительно нужны.
- Исторические блоки не удалены: по умолчанию каталог показывает canonical и
  user-блоки, а 955 imported-фрагментов доступны через отдельный legacy-режим с
  предупреждением.
- Для внешнего письма Workbench по умолчанию предлагает сохранить готовый HTML.
  Это честная модель: автоматическая конвертация произвольного HTML в хороший
  поддерживаемый Pug/Stylus не гарантируется.
- Иконки-кнопки получили текстовые подсказки; статический аудит не нашёл
  дубликатов ID или кнопок без обработчика на основных поверхностях.

## Где реально используется AI

### Без AI

- drag-and-drop, дерево и инспектор конструктора;
- Pug/Stylus-компиляция, CSS-inlining и media queries;
- обычное сохранение и открытие письма;
- переключение уже собранной локали;
- подстановка существующих locale JSON/TXT;
- RTL-постобработка;
- валидация структуры и HTML.

### Только по явному действию пользователя

- чат и Agent mode;
- анализ дизайна и создание черновика;
- перевод, исправление локали и расстановка плейсхолдеров;
- HTML → Pug assistance;
- создание новой локали через OpenAI;
- генерация/вариация изображения;
- AI-редактирование существующего письма.

Draft-flow может последовательно вызвать анализ дизайна, генерацию письма и
переводы. Agent mode может выполнить до 12 model-steps. Это должно быть явно
показано до запуска вместе с приблизительной стоимостью.

Раньше свободный текст Workbench иногда вызывал отдельную AI-классификацию до
основного ответа. Теперь дополнительный вызов разрешён только для неоднозначной
команды, одновременно содержащей локализационный контекст и действие. Обычный
разговор сразу идёт в discussion.

Текущий `/api/status.tokenUsage` охватывает не все пути (в частности, требуется
полностью подключить Agent, locale-AI и image generation). До этого счётчик
нельзя считать финансовым отчётом.

## Почему интерфейс казался медленным

Основная причина — не AI, а build pipeline:

1. Каждое изменение canvas после debounce запускало отдельный Node-процесс.
2. Полностью выполнялись Stylus, Pug, CSS trim/inlining и сборка EN.
3. `--pretty` запускал дорогую часть второй раз, хотя iframe читал compact HTML.
4. Видимые миниатюры каталога могли одновременно запустить много таких сборок.
5. В Workbench ввод с debounce 2 секунды сохраняет исходник и делает полный
   build; переход с dirty-локали специально ждёт точную сборку.

Контрольный локальный замер после оптимизации: холодный preview около `0.765 s`,
повтор идентичного содержимого около `0.0015 s` из кэша. Это хороший результат
для текущей архитектуры, но следующий этап — content-hash/no-op в Workbench и
предсобранные миниатюры.

Целевой performance budget для 1.0:

| Событие | Цель |
|---|---:|
| Локальная реакция поля/drag | < 100 ms |
| Cached preview | < 300 ms |
| Cold constructor build | < 2 s |
| Чистое переключение готовой локали | < 300 ms |
| Долгая операция | progress + cancel после 300 ms |

## Библиотека блоков

Снимок: 975 блоков, из них 18 canonical, 2 user и 955 imported. Imported — это
не готовая дизайн-система, а археология старых писем. Многие фрагменты:

- содержат картинки и тексты конкретной кампании;
- опираются на родительскую таблицу, которой нет в отдельно вставленном inner;
- используют общие классы и CSS исходного письма;
- несут namespace старого письма;
- похожи визуально, но имеют разные скрытые зависимости.

Поэтому базу нельзя просто очистить и нельзя смешивать целиком с canonical.
Правильный lifecycle:

`imported/quarantine → candidate → validated → canonical → deprecated`.

Для promotion в canonical блок должен пройти:

- standalone compile;
- desktop/mobile visual check;
- проверку слотов и отсутствия campaign namespace;
- проверку вложенности `outer → section → inner`;
- RTL-regression;
- проверку уникальности/области CSS-классов;
- thumbnail и понятное описание.

Комбо хранится как рецепт дерева, а не как непрозрачный HTML: после вставки его
section и inner-дети остаются самостоятельными. Ручной блок использует ту же
схему и после сохранения ведёт себя так же, как canonical.

## Конструктор: целевая модель

- `outer` — один контекст письма: scaffold, фон вокруг письма, preheader.
- `section` — самостоятельный ряд, который можно переставлять между секциями.
- `inner` — текст, изображение, логотип, кнопка, колонки, локальный spacer.
- `combo` — готовый рецепт из section/inner, после вставки полностью разложенный
  в дерево.

Левая панель должна быть контекстной, но предсказуемой:

- добавили готовую section/combo при включённом `Авто → Внутри` — открываются
  inner-блоки для продолжения этой секции;
- просто выбрали существующий блок — вкладка сама не прыгает;
- drag/drop всегда показывает конкретного родителя и слот до отпускания;
- несовместимый уровень не «угадывается» молча, а предлагает создать нужную
  section-обёртку.

## Локали и RTL

Правильный источник правды — Pug/Stylus + locale data. HTML локали является
производным артефактом, пока пользователь явно не нажал «Редактировать эту
локаль». После прямой HTML-правки локаль получает состояние `detached`; возврат
к исходникам удаляет override и снова собирает её из Pug.

Для 1.0 нужны статусы на каждой локали:

- `source`, `built`, `dirty`, `detached`, `invalid`, `missing`;
- время и source hash последней сборки;
- расхождение namespace/числа блоков;
- направление LTR/RTL и факт RTL-прохода.

AR/UR-регрессия была вызвана глобальным зеркалированием framework CSS. Теперь
CSS/media queries в `<head>` сохраняются, а меняются только точечные inline-
стили и текстовые элементы. Сырые `${{ rfm-... }}$` на арабском screenshot были
не RTL-багом, а отсутствующим JSON namespace из старого canonical-комбо.

## Pug, Stylus и HTML

Фактический build pipeline:

`Stylus → PostCSS split → Pug → CSS trim → inline-css → locale → RTL`.

Обычные CSS-правила попадают в inline `style`, а `@media`, `@supports`,
`@font-face`, keyframes и charset остаются в `<head>`. Это проверяется отдельным
интеграционным тестом. Визуальная совместимость с Gmail/Outlook/Apple Mail —
другая задача: браузерное preview не является доказательством email-client
совместимости.

Правило владения кодом:

- Pug/Stylus — основной редактируемый источник;
- compiled HTML — preview/export;
- прямой HTML edit — локальный detached override с явной кнопкой возврата;
- внешнее HTML-письмо по умолчанию импортируется как готовый HTML;
- конвертация external HTML в Pug всегда preview + diff, а не тихая подмена.

## UX и кнопки

Статически проверено:

- Constructor: 29 button-control, 20 явных ID;
- Workbench: 118 button-control, 105 явных ID;
- duplicate IDs и необработанные статические ID не найдены;
- неоднозначные icon-only close controls получили `title`.

118 кнопок не означают, что все одновременно лишние: часть находится в модалках
и контекстных панелях. Но для 1.0 верхняя панель должна показывать только
основной путь:

`Открыть → Править → Проверить → Собрать → Экспортировать`.

Редкие действия следует убрать в `Ещё`, а experimental/AI-команды — в отдельную
панель с объяснением результата. Любая destructive-кнопка должна показывать
объект действия и иметь undo/soft-delete.

## Release gates

### P0 — обязательно до 1.0

- Postgres/S3-совместимое постоянное хранилище: Heroku filesystem эфемерен.
- Версии письма и атомарный undo/restore для source, locale и detached HTML.
- One-click preflight: build всех локалей, unresolved placeholders, ссылки,
  alt, размеры, namespace, RTL, HTML-аудит.
- Матрица реальных клиентов: Gmail web/app, Outlook desktop/web, Apple Mail;
  хотя бы screenshot service + сохранённые baselines.
- Cancel/AbortSignal для активных build и OpenAI операций.
- Полная AI-метрика: feature, model, calls, tokens, latency, errors, cost.
- Auth/roles и журнал: кто открыл, изменил, применил AI, собрал, экспортировал.
- Release manifest: source commit/hash, locale hashes, build version и дата.

### P1 — сразу после стабилизации P0

- Workbench content-hash/no-op вместо сборки при неизменном source.
- Разделение base compile и быстрой locale materialization.
- Предсобранные thumbnails вместо build на scroll.
- Promotion UI для legacy-блоков с автоматическими тестами.
- Namespace registry и автоматическая миграция reusable literals в namespace.
- Diff/accept/reject для каждого AI-изменения, а не только общий результат.
- История assets: где используется картинка, замена по ссылкам, orphan cleanup.

### P2 — развитие после 1.0

- AI compose из validated canonical blocks с планом до сборки.
- Cross-locale semantic QA и translation memory.
- Генерация/вариации картинок с brand guardrails и asset provenance.
- Email-client-aware советы по коду и автоматические безопасные фиксы.

## Рекомендуемый порядок следующих итераций

1. Закрепить текущие исправления регрессионными тестами и smoke на staging.
2. Добавить version/undo + release manifest.
3. Реализовать единый preflight всех локалей и unresolved placeholders.
4. Подключить durable storage до следующего production deploy.
5. Добавить реальную email-client screenshot matrix.
6. После этого расширять AI, не раньше: сначала diff/cost/cancel/telemetry.

На этом уровне проект можно честно назвать `0.9 release candidate`. Версия `1.0`
должна означать не только богатый интерфейс, но и воспроизводимое письмо, которое
можно восстановить, проверить и безопасно отправить.

## Дополнение от 2026-07-16

После повторной интеграционной проверки закрыт следующий слой RC-работ:

- намеренная очистка старой базы сохранена: удалённые письма не восстановлены;
  основной список ограничен `X_IQ`, `X_IQBroker` и рабочими собранными письмами,
  `X_System` доступен только через «Архив», а `X_preview` остаётся служебным;
- любой блок получил единый inspector «Поверхность»: фон доступен для `outer`,
  `section`, `inner` и обоих разделителей; для section/inner также доступны
  безопасные border, radius и padding;
- fresh compose больше не наследует campaign-specific preheader
  `welcome-broker.block_00` из scaffold. Явный round-trip существующего исходника
  может сохранить его отдельно;
- ручные блоки получили состояния `draft → candidate → approved`: Pug, Stylus,
  слоты и токены сначала проверяются детерминированно, затем пользователь
  подтверждает визуальный результат. AI-review остаётся необязательной подсказкой;
- переход Constructor → Workbench теперь сразу гидратирует редактируемый
  `header.pug`; действие плейсхолдеров работает с Pug/Jade source, Stylus остаётся
  соседним исходником;
- compiled HTML связан с Pug и read-only. Ручная правка требует явного detach,
  хранится как override конкретной локали и может быть сброшена обратно к Pug;
- безопасный RTL-контракт `text` применяется по умолчанию после CSS-inlining:
  геометрия таблиц, изображения, padding, float, background и порядок колонок не
  меняются; направление и выравнивание задаются текстовым узлам. Полное
  зеркалирование сохранено как явный режим `mirror`;
- отсутствующие locale namespace теперь показываются как
  `missing-localization-data`: RTL не выдаётся за перевод и не скрывает сырой
  placeholder;
- пустые CSS-декларации вида `padding-left:;` удаляются до Pug-build.

Финальная проверка этого прохода: основной regression chain, 115 RTL-сценариев,
29/29 блоков, дерево конструктора, style slots, lifecycle пользовательских
блоков, active-base policy, Pug/HTML lifecycle, локализация, CSS-inlining и
media queries прошли. В браузере отдельно подтверждены контекстный каталог,
уровни обоих разделителей, фон `#F9F9F9`, Pug-first deep-link, HTML detach/reset
и явная диагностика отсутствующего AR namespace.

Это не снимает P0-гейты выше. В частности, старые AR/UR `dist` с RTL-маркером
первой версии нужно пересобрать из Pug/Original, а недостающие namespace-файлы —
наполнить новыми переводами. Уже мутированный старый HTML нельзя надёжно
«раззеркалить» без исходника.

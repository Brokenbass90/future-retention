# План: чистая база, честные превью, свой агент у каждого

Дата: 2026-09-13. Статус: проект на согласование, код не тронут.

Документ отвечает на четыре вопроса: что не так с базой писем, почему криво
рендерятся превью, как развести нескольких людей с их личными Клодами и что
именно агент должен видеть и уметь в студии.

---

## 0. Что измерено, а не предположено

| Что | Факт |
|---|---|
| Писем в базе | X_IQ 47, X_IQBroker 24, X_System 19 = **90** |
| Мусорные бренды | X_TestBrandFixture (0 писем), X_assembled (5 демо), X_preview (2 демо) |
| Вес брендов | 18 МБ |
| Файлов в одном письме | ~29 |
| Из них уникальных | **2–3**: `app/templates/blocks/header.pug`, `app/styles/blocks/main.styl`, иногда `head-extra.styl` |
| Остальные 26 | побайтово одинаковы во всех письмах: `head.jade`, `footer.jade`, `button.jade`, `ink.styl`, `variables.styl`, `mixins.styl`, `common.styl` — по 47 копий, **1 уникальная версия** каждой |
| `index.jade` | 42 копии, 1 уникальная версия |
| Legacy-дубли | `.jade` 740 файлов против `.pug` 187 |
| Скомпилированный вывод в git | 203 папки `dist/`, 150 `.html` |

Вывод: база — это не 90 писем, это 90 копий одного скелета, в каждой из
которых осмысленны два файла. Всё остальное уже лежит в `email-base/vendor/`.

## 1. База писем

### Что делаем

**Каноническое письмо** — только то, что действительно про это письмо:

```
email-base/<BRAND>/<mail>/
  mail.json         бренд, набор (promo|system), тип, происхождение, версия
  blocks.pug        бывший app/templates/blocks/header.pug
  blocks.styl       бывший app/styles/blocks/main.styl
  overrides/        ТОЛЬКО то, что реально разошлось с vendor (обычно пусто)
```

Всё прочее — `head`, `footer`, `button`, `preheader`, `mixins`, `ink`,
`variables`, `common` — сборщик берёт из `vendor/`. Локали и так уже общие
(`vendor/data/<locale>/*.json`), их не трогаем.

### Как переносим, чтобы ничего не потерять

Миграция идёт файлом-за-файлом по хешам, а не «удалим всё лишнее»:

1. Собрать **все 90 писем как есть** и сохранить HTML каждой локали — это эталон.
2. Для каждого файла письма посчитать хеш и сравнить с файлом из `vendor/`.
   Совпал — удаляем. Не совпал — переезжает в `overrides/` и попадает в отчёт
   расхождений (их надо будет глазами посмотреть, это и есть настоящая работа).
3. `.jade` удаляем там, где есть `.pug` с тем же содержанием; где `.pug` нет —
   конвертируем и сверяем результат сборки.
4. `dist/` из базы выносим целиком: это вывод, ему не место в исходниках.
5. Пересобрать все 90 писем и **сравнить с эталоном побайтово**.

### Ворота

`scripts/test-mail-base-migration.mjs`: миграция считается успешной, только
если HTML всех писем во всех локалях совпал с эталоном до символа. Не совпало
хоть одно — миграция откатывается, а письмо попадает в список «разобраться
руками». Это единственный способ снести 2400 файлов и спать спокойно.

### Сразу в мусор (без миграции)

`X_TestBrandFixture`, `X_preview`, `X_assembled` — это следы тестов, не письма.

## 2. Превью блоков

### Что реально сломано

Смотрел на готовые PNG, не на код:

1. **`sys-footer`** показывает `{{embedded.company_address}}` и
   `{{embedded.risk_warning}}` буквально. Превью рендерится без подстановки
   vendor-переменных — человек в каталоге видит фигурные скобки вместо адреса.
2. **`sys-button`** обрезан не по содержимому: кнопка стоит не по центру кадра,
   вокруг неравные поля. Кадрирование по фиксированному прямоугольнику, а не по
   реальным границам блока.
3. 35 превью из 540 весят меньше 1.5 КБ. Часть законно (спейсеры), часть —
   пустые кадры, которые надо разобрать поимённо.

### Как правильно

Превью должно рендериться **тем же конвейером, что и настоящее письмо**, а не
упрощённым. Значит:

- словарь демо-значений `vendor/data/_preview.json`: адрес, риск-ворнинг,
  имя, ссылки — всё, что письмо подставляет из vendor;
- подстановка `${{ ns.x }}$` и `{{embedded.x}}` перед скриншотом;
- кадрирование по фактическим границам содержимого блока (bounding box), а не
  по заранее заданному прямоугольнику;
- фон кадра — фон бренда из темы, а не белый по умолчанию.

### Ворота

`scripts/test-block-previews-clean.mjs`: ни одно превью не содержит `{{` или
`${{` (проверяем по тексту, снятому со страницы перед скриншотом), ни одно
превью не пустое, у каждого блока каталога есть desktop и mobile.

## 3. Несколько человек — несколько Клодов

Сегодня студия однопользовательская: одна файловая система, одна пара
Basic Auth, никакого понятия сессии (`session` встречается в `server.js`
дважды, и оба раза не про это). Пока людей двое, они молча топчут файлы друг
друга.

### Рабочее пространство

Вводим **workspace** — личное пространство человека:

```
.retkit-workspaces/<token>/
  drafts/      его черновики писем и блоков
  canvas.json  его холст конструктора
  inbox.json   очередь сообщений его агенту (см. п. 4)
```

- Токен выдаётся при первом входе и живёт в браузере.
- Мастер подключения **вшивает токен в конфиг MCP** (`RETKIT_TOKEN`) — то есть
  Клод конкретного человека приходит в студию уже представленным.
- Общая база (`email-base`, `data/block-library`) для агента **на чтение**;
  запись туда — только через публикацию из своего workspace и только с
  подтверждением человека.

Это одновременно решает три вещи: люди не мешают друг другу, у каждого свой
агент, и появляется адрес, по которому чат может найти нужного Клода.

## 4. Чат: одно окно, две поверхности

### Кнопка

В конструкторе `💬 Спросить ИИ` из верхней панели убираем. Внизу справа —
круглая кнопка-пузырь (FAB), по нажатию открывается то же самое окно чата, что
и в работе с кодом. Один компонент `StudioChat`, две точки монтирования;
отдельная реализация `ai-drawer` в воркбенче уходит. Контекст разный
(конструктор знает холст, код знает открытый файл и локаль), сущность одна.

### Как разговор попадает к личному Клоду — честно

MCP устроен так: модель живёт в клиенте (Claude Desktop / Claude Code), студия
— сервер инструментов. Сервер сам по себе не может «позвать» модель. Поэтому
из окна студии разговор идёт **через реле**:

1. Человек пишет в окно студии → сообщение кладётся в `inbox` его workspace.
2. У его Клода есть инструмент `retkit_wait_for_message` (длинный опрос) —
   он забирает сообщение.
3. Клод работает инструментами студии и отвечает через `retkit_reply` →
   ответ появляется в том же окне.

Цена: человек один раз говорит своему Клоду «работай со студией, жди
сообщений». Дальше окно студии ведёт себя как обычный чат.

Апгрейд, который **не обещаем заранее**: MCP умеет sampling — сервер просит
модель клиента сгенерировать ответ, и тогда реле не нужно вовсе. Поддержка
sampling у клиентов неровная, поэтому делаем реле, а sampling включаем, если
клиент его объявил.

## 5. Что агент видит и чем управляет

Принцип: не вываливать репозиторий, а дать узкий именованный набор
инструментов по доменам. Агент видит ровно рабочую поверхность человека.

### Конструктор
- каталог блоков и карточка блока (уже есть);
- **холст**: прочитать дерево, добавить/переместить/удалить блок, выставить слот;
- собрать письмо и получить HTML или скриншот — то же, что человек видит справа;
- создать новый блок и исправить существующий;
- сохранить / удалить письмо — **через подтверждение**.

### Код
- «чистый» вид открытого письма: `blocks.pug` + `blocks.styl`, без `dist/`,
  без `.jade`-двойников, без vendor-шума — то самое, ради чего затевалась
  чистка базы в п. 1;
- правка файла, пересборка, готовый HTML и скриншот предпросмотра;
- разбор по кускам: какой фрагмент кода какому блоку письма соответствует
  (маркеры `rk:block-start` для этого уже есть).

### Локали
- список локалей письма и содержимое каждой;
- сверка с оригиналом: где плейсхолдер не подтянулся и почему;
- правка перевода, создание новой локали;
- всё это обсуждаемо в чате по-человечески: «что не так с арабской?».

### Конвейер рендера
- прочитать конфиг сборки (gulp, vendor-стили) и **предложить патч**;
- применение — только с подтверждением: это меняет все 90 писем разом.

### Картинки и макеты — где граница
- **Работает сейчас**: библиотека ассетов (поиск, вставка), обрезка и
  ресайз, вставка по ссылке, разбор макета, который человек приложил в своём
  клиенте картинкой.
- **Нужен отдельный трек**: генерация картинок. Клод не рисует; нужна либо
  локальная модель, либо ключ к сервису генерации. Это честно отдельная задача,
  а не «включим галочку».
- **Figma по ссылке**: нужен личный токен Figma человека; по токену забираем
  ноды и картинки. Ключ его, платит он, студия ничего не хранит.

---

## 6. Подтверждения

Опасные инструменты (удаление, перезапись чужого, правка конвейера) не делают
работу сразу. Они возвращают `{ needs_confirmation, token, diff }`, студия
показывает поднос ожидающих операций, и ничего не происходит, пока человек не
нажмёт «применить». Агент при этом видит, что операция висит, и может
объяснить, что именно она сделает.

---

## 7. Порядок работ

1. **Workspace + токен + подтверждения** — пол, на котором стоит всё
   остальное, и защита от того, что двое сотрут работу друг друга.
2. **Круглая кнопка и один чат** + реле к личному Клоду.
3. **Карта инструментов** по доменам из п. 5.
4. **Чистка базы** с воротами «HTML побайтово тот же».
5. **Превью** с подстановкой и кадрированием по содержимому.

Пункты 4 и 5 можно двигать вперёд, если чистая база нужна раньше: они ни от
чего в списке не зависят.

## 8. Что не трогаем

- `vendor/` и `vendor/data` — источник и локали; чистка базы их не касается.
- Формат блоков библиотеки — он проверен тестами, ломать его под агента нельзя.
- Существующие письма до тех пор, пока ворота миграции не зелёные.

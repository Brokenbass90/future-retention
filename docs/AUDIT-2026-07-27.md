# Аудит Future Retention Studio и фронт работ — 2026-07-27

Аудит по факту кода и данных на диске, без опоры на прошлые хендоффы.
Все цифры получены прогоном по репозиторию, скрипты воспроизводимы.

---

## 0. Резюме в трёх строчках

1. **Превью блоков в конструкторе не «сломано» — его архитектурно нет.** Есть live-iframe,
   который на каждую карточку запускает полную сборку письма (~1.6 с в подпроцессе),
   молча прячет карточку при любой ошибке и физически не может показать пустую
   секцию-обёртку. Ни человек, ни AI внешний вид блока не видят.
2. **Стили блока не принадлежат блоку.** Блок опирается на `main.styl` семьи,
   где одни и те же имена классов значат разное: `.h-406` имеет **18 разных**
   определений (280px, 336px, 380px, 394px…), `.title` — 5, `.text` — 5.
   Поэтому блок, вырезанный из одной семьи, в другой едет.
3. **База писем действительно нерелевантна.** 117 писем, из них 23 — дубли
   `-old/-copy/-copy-2/«134 2»`; собранный dist есть у ~25. В каталоге блоков
   964 из 1029 позиций — импорт, и **517 из них (54%)** привязаны к брендам,
   которых в базе больше нет.

## 3. Стили — корневая архитектурная проблема

### 3.1 Как устроено сейчас

```
app/styles/common.styl
  ├── helpers/ink.styl        ← фреймворк (Ink/Zurb), 149 классов, общий
  ├── helpers/footer|variables|mixins
  ├── roboto-font.css
  └── blocks/**/*             ← main.styl семьи (у скелета — 916 строк)
```

`composeEmailFromBlocks` берёт скелет `X_IQBroker/mail-welcome`, копирует его
`blocks/main.styl` целиком и **дописывает** в конец styl-куски блоков.

### 3.2 Почему это не работает

**Классы глобальные, и их смысл зависит от семьи.** Замер по всем 117 письмам:

Цифры ниже — из реестра стилей (`npm run styles:registry`), который компилирует
Stylus в CSS и разбирает postcss'ом. Первая прикидка регулярками (478 из 532)
была завышена: она считала медиа-варианты за отдельные смыслы. Точные данные:

**675 классов · 70 441 правило · 118 писем · 133 класса имеют больше одного
базового смысла в слое семьи.**

| класс | базовых смыслов | из них медиа | примеры |
|---|---|---|---|
| `.bgr-image` | **36** | 1 | 36 разных фоновых картинок под одним именем |
| `.b-new-section-03` | 18 | 0 | то отступ, то шрифт 18px, то заголовок 26px |
| `.h-406` | **16** | 15 | `height 280px` / `300px` / `336px` / `394px` |
| `.columns` | 16 | 5 | `width auto` / `74px` / `152px` |
| `.text` | 16 | 2 | 18px/26px #393A44 · 18px/28px #3c3939 · просто `font-weight 700` |
| `.left-block` / `.right-block` | 10 / 10 | 8 | карточка 224px / колонка 49% / мобильный сброс |
| `.m-w` / `.column` | 10 / 10 | 0 | 78px / 49px / 70px |
| `.m-w-2` | 2 | 0 | 48px (семья 234) / 74px (семья 325) |

Прошлая сессия уже наступила на это (`m-w-2` пришлось намеренно не
использовать, чтобы 325 и 234 не подрались в одном письме) — но это лечилось
точечно, а не системно.

**Даже «фреймворк» не один.** `helpers/ink.styl` существует в базе в трёх
разных редакциях: 81 письмо на одной, 25 на второй, 12 на третьей.

**Попутно нашлось битое.** `X_IQ/mail-rfm-313-copy/app/styles/blocks/main.styl`
содержит не Stylus, а HTML-страницу (`<!DOCTYPE public><html …`). Письмо в базе
числится целым, но его стили не компилируются в принципе.

**Блок не декларирует, что ему нужно.** В `styl` блока лежит только то, что
автор блока туда положил руками. Классы вроде `pt44`, `center`, `m-w`, `h-*`
приходят «в подарок» от скелета. Отсюда два следствия:

- если compose перезапишет `main.styl` — вёрстка рассыпется (это уже случалось,
  фикс от 2026-07-21 — конкатенация скелета);
- текущий фикс = **каждое письмо тащит все 916 строк CSS чужой семьи**,
  из которых `trimCss` потом вычищает неиспользуемое. Работает, но смысл
  класса всё равно берётся из случайной семьи.

**103 из 117 писем используют классы, для которых CSS нет нигде** — ни в блоке,
ни в семье, ни во фреймворке. Топ: `last-link`/`first-link` (78 писем),
`plr10a` (46), `centet` — опечатка от `center` (34 письма), `apps` (20),
`base-bg` (19), `w100` (11), `h-406` (6). То есть часть разметки уже сейчас
рендерится без стилей и никто этого не замечает.

### 3.3 Переопределения: что уже работает, а что нет

Требование: у блока есть дефолтные стили, но в конкретном письме их надо уметь
переопределить — либо взяв готовый блок и задав ему другие параметры, либо
дописав стили руками именно для этого письма.

Замер на живой сборке (два экземпляра `iq-text-title` с разным `title_color`):

| | сейчас |
|---|---|
| Переопределение долетает до HTML | ✅ да — `<p style="color:#123456">` и `#abcdef` |
| Почему работает | автор блока протянул `{{ title_color }}` в inline-атрибут `style=` |
| Что происходит с классами | `styl` блока эмитится **на каждый экземпляр**: в `main.styl` попадают `.iq-middle-title{color:#123456}` и `.iq-middle-title{color:#abcdef}` — конфликт, последний побеждает |
| Спасает только | inline-стиль, который сильнее класса |

Отсюда три дыры:

1. **Переопределить можно только то, что автор блока заранее объявил слотом**
   и вручную протянул в inline-стиль. Свойства, живущего только в классе,
   на экземпляре не поменять.
2. **`styl` дублируется по числу экземпляров** и конфликтует сам с собой.
   Пока значения совпадают — незаметно; как только разошлись — тихо ломается.
3. **Слоя «стили этого письма» нет вообще.** `compose` пишет в
   `blocks/main.styl`, поэтому любая ручная правка стилей письма теряется при
   следующем сохранении из конструктора.

Плюс масштаб: в замере скелетная часть composed-CSS — **16.6 КБ**, блочная —
**1.5 КБ**. То есть 92% стилей письма — это `main.styl` чужой семьи, притащенный
целиком и вычищенный уже на сборке.

### 3.4 Что должно быть — четыре слоя каскада

```
0. Фреймворк      vendor/styles + ink          глобально, всегда, один на всех
1. Дефолты блока  styl блока, классы в скоупе  ОДИН раз на блок, не на экземпляр
2. Экземпляр      слоты + свободные overrides  inline + класс .блок--uid
3. Стили письма   app/styles/blocks/custom.styl  руками, переживает пересохранение
                                                  из конструктора
```

Что это чинит:

- **Дефолты живут в одном месте.** Класс блока эмитится один раз — конфликт
  двух экземпляров исчезает как класс проблем.
- **Переопределить можно что угодно, а не только объявленные слоты.**
  У экземпляра появляется свободная форма `styleOverrides`; простые свойства
  уезжают в inline (для почты это и правильно), а то, что inline не умеет —
  медиазапросы, псевдоклассы — в персональный класс `.iq-text-title--u3f7`.
- **Ручные стили письма перестают затираться.** `compose` владеет только
  `main.styl`; `custom.styl` — территория человека, подключается последним и
  бьёт всё, кроме inline.
- **«Чего нет — не подтягивается».** В письмо едут стили только тех блоков,
  что реально стоят в дереве, плюс фреймворк. `trimCss` на сборке остаётся
  страховкой, а не механизмом выживания.

### 3.5 Реестр стилей — сделано

`src/style-registry.js` + `npm run styles:registry` компилируют Stylus всей базы
в CSS и строят индекс `класс → варианты правил` с пометкой слоя
(фреймворк/семья) и источников. Умеет:

- `lookupClass("h-406")` — все 16 смыслов класса с источниками
  (`npm run styles:report`, или `--class h-406`);
- `rulesForClasses([...], { preferSource })` — собрать CSS для втягивания
  внутрь блока, выбрав вариант конкретного письма при многозначности;
  фреймворковые классы не дублируются;
- `conflictReport()` / `conflictSummary()` — что именно многозначно.

Это фундамент автоскоупа: при нарезке блока мы теперь можем вытащить в него
ровно те правила семьи, на которые он опирается.

### 3.6 Что должно быть (принятое решение — автоскоуп)

1. **Реестр стилей студии.** Единый индекс `класс → правила` по всему, что есть:
   `ink.styl` (фреймворк) + `vendor/styles/*` + все `main.styl` всех семей,
   с пометкой источника и с явным списком конфликтов. Сейчас такого индекса нет —
   есть только `src/vendor-mixins-ref.js`.
2. **Блок самодостаточен.** При импорте/сохранении классы блока префиксуются
   (`.iq-b7f3__title`), а нужные правила вытягиваются из реестра **внутрь**
   `styl` блока. Блок перестаёт зависеть от того, в какой скелет его положили.
3. **Компоновка = сумма блоков.** `compose` перестаёт копировать `main.styl`
   семьи; CSS письма = фреймворк + стили ровно тех блоков, что стоят в дереве.
   `trimCss` остаётся страховкой, а не механизмом выживания.
4. **Валидатор.** Блок не сохраняется, если использует класс, которого нет ни
   в его `styl`, ни во фреймворке. Это закрывает историю с `centet` навсегда.

## 5. Превью блоков — что именно не так

Механизм в `public/constructor.js`: `IntersectionObserver` → `loadBlockThumb()` →
`POST /api/compose-preview` → `composeEmailFromBlocks` + `spawn(build-mail.js)` →
готовый HTML в `<iframe srcdoc>` с `transform: scale(.43)`.

| # | Дефект | Следствие |
|---|---|---|
| 1 | Полная сборка письма на каждую карточку (~1.6 с, подпроцесс) | при 1 029 блоках каталог захлёбывается очередью сборок |
| 2 | Кэш — `Map` в памяти вкладки | перезагрузил страницу — всё пересобирается заново |
| 3 | `placement: "outer"` → `display: none` | обёртки вообще без превью |
| 4 | Секции-обёртки рендерятся пустыми | визуально неотличимы друг от друга |
| 5 | Любая ошибка → тихий `display: none` | сломанный блок выглядит как нормальный |
| 6 | Жёсткий кроп 600×760 при `scale(.43)` | у атомов видна пустота, у длинных блоков — обрезок |
| 7 | Нет мобильного вида | а адаптив — половина работы верстальщика |
| 8 | AI не получает ничего визуального | `design-compose` выбирает блок по хардкод-таблице `PREFERRED_BLOCK_BY_CATEGORY` и тексту описания |

Пункт 8 — ключевой для «чтобы система понимала, что это за блок».

### Оператор не мог изменить письмо — исправлено

На просьбу «сдвинь кнопку в хедере влево» агент вызывал `edit_locale_block` и
`save_user_block`, отвечал «сейчас изменю слот» — и не менял ничего. Причина не
в модели: **у поверхности конструктора не было ни одного инструмента записи**.
Канвас живёт в браузере, агент работает на сервере, моста между ними не было.
Из доступного агент выбирал похожее по названию — файлы переводов и общую
библиотеку блоков. Хуже, чем ничего: правка библиотеки задела бы все письма,
где стоит этот блок.

**Инструмент `update_canvas_block`.** Меняет слоты и оформление блока,
который уже стоит на канвасе, по его uid. Ничего не пишет сам: копит операции
в контексте, сервер отдаёт их клиенту в финальном кадре, клиент применяет и
перерисовывает превью. Весь пакет правок — **одна отмена**: человек сказал одну
фразу, откатывать он тоже захочет одним Ctrl+Z. Несуществующий uid не роняет
ничего, а возвращает агенту список доступных.

В системный промпт добавлено прямым текстом: на поверхности конструктора
`edit_locale_block` и `save_user_block` использовать нельзя — первый правит
переводы, второй общую библиотеку, и ни один не меняет письмо перед глазами.

**Дубли ответов.** Агент отдаёт итог дважды — сначала кадром `text` по ходу
работы, потом тем же текстом в `final.summary`. Панель показывала оба.
Теперь сверяем с последним сообщением.

**Мелочи из консоли.** `/favicon.ico` отдаётся из `favicon.svg` — красная 404
на каждой загрузке ушла. Сообщения `Blocked script execution in 'about:srcdoc'`
— это песочница iframe штатно блокирует скрипты из старых писем; не ошибка
студии, а защита, которая работает как задумано.

### Хранилище картинок — сделано (кроме подключения бакета)

**Поправка к тому, что я написал раньше:** я утверждал, что `data/assets`
наружу не раздаётся. Это неверно — маршрут `GET /studio-assets/<файл>` есть
давно, я искал не по тому имени. Реальная проблема уже: адрес **относительный**,
и в письме, которое откроют в почте, картинка по нему не загрузится.

Что сделано:

| Что | Где |
|---|---|
| Адаптер хранилища с двумя драйверами | `src/asset-storage.js` |
| `local` — диск + `/studio-assets/…` | по умолчанию, для разработки и превью |
| `s3` — R2 / S3 / Spaces, постоянный публичный URL | по переменным окружения |
| Подпись SigV4 вручную | без зависимости от aws-sdk ради одного PUT |
| Загрузка и ИИ-генерация пишут через адаптер | `registerUploadedAssets` в `server.js` |
| Статус хранилища для UI | `GET /api/assets/status` |
| Переменные с пояснениями | `.env.example` |
| 23 теста | `scripts/test-asset-storage.mjs` |

Главное правило, зашитое в адаптер: **локальный путь не выдаётся за публичный
адрес**. `absoluteAssetUrl` для локального драйвера возвращает `null`, а статус
прямо говорит, что в рассылке такие картинки не покажутся. Лучше честный отказ,
чем битая ссылка у получателя. И если `ASSET_STORAGE=s3` настроен не полностью,
загрузка падает понятной ошибкой, а не сползает молча на локальный диск —
иначе на проде картинки тихо перестали бы быть публичными.

**Реестр пересинхронизирован: 9 записей → 99.** По дороге выяснилось, что
источник правды — не `data/asset-registry.json` (он остался от прежней схемы и
сервером не читается), а таблица `asset_registry` в SQLite. Первая версия
скрипта писала в мёртвый файл; исправлено, скрипт пишет в базу
(`npm run assets:resync` — показать, `assets:resync-apply` — записать).

### Хранилище картинок — исходный разбор

Проверено по коду, не по памяти:

| Есть | Где |
|---|---|
| Загрузка файлов | `POST /api/assets/register` → `data/assets/` |
| Генерация картинки ИИ | `POST /api/assets/generate` (нужен `OPENAI_API_KEY`) |
| Реестр с alt, ключом, размещением | `data/asset-registry.json` |
| Список для UI | `GET /api/assets` |

**Чего нет — и это главное:** у загруженного файла **нет публичного URL**.
`data/assets` наружу не раздаётся (`serveStatic` отдаёт только `public/`),
поэтому в настоящем письме такая картинка не покажется никому. Поле
`externalUrl` в реестре подтверждает исходную задумку: ссылку предполагалось
приносить со стороны, а студия хранила только локальную копию для превью.

**Ещё два факта:**

- Реестр рассинхронен с диском: **18 записей на 99 файлов** (23 МБ).
  Файлы копились, реестр — нет.
- На Heroku диск эфемерный (это прямо написано в `HEROKU-DEPLOYMENT.md`):
  всё, что загружено через UI, пропадает при следующем деплое.

**Решение — S3-совместимое хранилище (R2 / S3 / Spaces).** План:

1. `src/asset-storage.js` — адаптер: `put(buffer, meta) → { url, key }`.
   Локальный драйвер (диск + раздача `/assets/*`) для разработки и
   S3-драйвер для хостинга, выбор по переменным окружения.
2. `register` и `generate` пишут через адаптер и кладут постоянный URL в реестр.
3. Слот картинки в конструкторе — выбор из библиотеки ассетов или загрузка
   прямо в поле; ИИ-оператор получает инструмент «сгенерировать и вставить».
4. Миграция 99 файлов + пересборка реестра по факту содержимого папки.

R2 предпочтительнее по деньгам: за исходящий трафик не берут, а картинки в
рассылке грузятся десятки тысяч раз.

### Про ошибки в консоли

На чистом профиле их **ноль** — проверил: три iframe в конструкторе, все с
`sandbox="allow-same-origin"`, скриптов в содержимом нет, сообщений

### Автоскоуп стилей блока (как устроен)

`src/scope-block-styles.js` + `npm run styles:scope` (сухой прогон) /
`styles:scope-apply` (запись). Что делает:

- свои классы блока переименовываются в `<id>--<class>`
  (`.gray-block` → `.iq-gray-step--gray-block`) — столкнуться с чужим уже не могут;
- правила, которые блок брал из `main.styl` семьи, **втягиваются внутрь** блока;
- фреймворковые классы (`.row`, `.columns`, `.wrapper`, `.center`) не трогаются:
  это общие примитивы, дублировать их в каждый блок бессмысленно, а
  переименовать — сломать скелет;
- если блок **дописывает поверх** фреймворкового класса (`.logo`, `.butt`,
  `.text-pad-small` — таких блоков 130), на элементе остаются **оба** имени:
  база из ink + скоупное правило блока. Иначе фреймворковая база потерялась бы;
- операция идемпотентна — повторный прогон не даёт `.demo--demo--x`
  (эту ошибку поймал тест, а не продакшн).

**Решения по многозначным классам — `data/style-decisions.json`.** Правило
выбора: берём вариант, с которым готовые комбо рендерятся *сейчас*

### Приоритет стилей — короткий ответ

Да, новое сильнее. Точнее — три уровня:

1. **После скоупа вопроса приоритета почти нет.** Классы нового блока
   называются `<id>--<class>`, старого — своим `<id>--<class>`. Это разные
   имена, они не конкурируют вообще. Раньше два блока дрались за `.title`,
   теперь у каждого свой.
2. **Где стили всё же складываются** (блок дописывает поверх фреймворка),
   правило блока идёт в CSS позже фреймворкового и побеждает.
3. **На уровне письма** порядок такой:
   `фреймворк → стили блоков → custom.styl письма → inline-стили блоков`.
   Каждый следующий бьёт предыдущий. Новый блок сильнее фреймворка, ручной
   `custom.styl` сильнее любых блоков.

Единственное исключение: свойство, которое блок пишет **инлайном** через слот
(цвет из инспектора), не перебивается ничем — так устроена почтовая вёрстка.
Менять его надо там же, где задали, — слотом.

### Как теперь работают стили письма

```
app/styles/
  helpers/ink.styl         фреймворк — общий, не трогаем
  blocks/main.styl         ← конструктор ВЛАДЕЕТ и перезаписывает
  custom.styl              ← человек владеет, конструктор не трогает НИКОГДА
```

Каскад: фреймворк → `main.styl` (скелет + стили блоков) → `custom.styl` →
inline-стили блоков.

Практический смысл: дефолт блока можно переопределить и слотом в конструкторе
(уедет в inline, сильнее всего), и руками в `custom.styl` (переживёт любое
пересохранение). Единственное, что `custom.styl` перебить не может, — свойство,
которое блок пишет инлайном; это ограничение самой почтовой вёрстки, и оно
описано прямо в шапке файла.
